# 发行准备

`.github/workflows/release.yml` 在推送 `v*` 标签时运行：先校验标签与 `mygo.json.version`，再在 macOS runner 上构建 `darwin/arm64`，把应用包与更新资产上传到同标签的草稿 Release，上传完成后自动发布并标记为 Latest。构建或上传失败时 Release 保持草稿。仓库不提供发行配置脚本或资产验签脚本；日常 Go 检查只做 CLI 验证，不执行应用 build。

发行构建不做 Apple 代码签名与公证：项目没有付费开发者团队，产物只有 ad-hoc 签名。这是明确的取舍，代价见下文“Gatekeeper”。

## 已确定的身份

- 发布仓库：`wan-kong/frpc`。
- Bundle ID：`top.wankong.frpc`。
- slug 与安装包名称前缀：`frpc`。
- 支持目标：`darwin/arm64`、`darwin/amd64`；CI 只发布 arm64，`make build` 仍可本地构建两架构。固定 MyGo 0.7.4，由 go.mod tool 提供 CLI。

代码、标签和版本元数据需先由项目所有者提交并推送。

## 版本与标签

版本只在 `mygo.json` 的 `version` 中维护。`make release` 执行 `bunx bumpp@12.3.0`（配置见 `bump.config.ts`）：提示选择 major/minor/patch，更新该字段，用 `changelogen` 在 `CHANGELOG.md` 顶部写入 `## v<version>` 小节，提交 `chore: release v<version>`，创建并推送 `v<version>` 标签。工作区不干净时直接拒绝。需要 bun，或改用 `npx bumpp@12.3.0`（Node 22.18+）。

`CHANGELOG.md` 同时供两处使用：workflow 把该版本小节写入 Release 的说明，`mygo build` 把同一小节写进更新 manifest，应用更新面板因此显示相同的更新内容。`CHANGELOG.md` 存在时，缺少当前版本小节会让 `mygo build` 直接失败。

不要在 bumpp 之后手动修改版本：workflow 会校验标签与 `mygo.json.version` 一致，不一致则不创建 Release。

## 仓库配置

只有一个 Repository Secret：

| 名称 | 用途 |
| --- | --- |
| `MYGO_UPDATER_PRIVATE_KEY` | 与 `mygo.json` 公钥配对的更新签名私钥 |

不需要 Repository Variables、证书或 Apple 公证账号。

## 更新签名

`mygo keygen` 已生成密钥，公钥写在 `mygo.json`：

```json
"updates": {
  "github": "wan-kong/frpc",
  "publicKey": "<mygo-update.pub 内容>"
}
```

私钥只通过 `MYGO_UPDATER_PRIVATE_KEY` 提供给打包环境，不得提交或随应用分发。丢失或更换私钥后，已安装版本无法再接受新更新。

## Gatekeeper

未签名（ad-hoc）应用从 GitHub 下载后带 quarantine 属性，Gatekeeper 会阻止直接打开。用户需在 Finder 中按住 Control 点击应用并选择“打开”。首次打开的手动步骤是未签名分发的既定限制；不以关闭 Gatekeeper 或全局 `xattr -cr` 作为安装指导。将来具备 Developer ID 时再在 `mygo.json` 配置 `macos.signingIdentity` 与 `notarize` 并恢复 CI 签名步骤。

## 发布后核对

发布不再等待人工检查草稿；workflow 只在构建与上传成功后把 Release 发布为 Latest，但发布即对客户端可见。

1. workflow 为 arm64 产出应用包、更新归档、增量包和 `update-darwin-arm64.json`；本地 `make build` 可另产 amd64。
2. 用 `codesign -dv`（应显示 ad-hoc）、`lipo`、`hdiutil` 核对签名类型、架构、Bundle ID 与版本。
3. 确认包内只有目标架构的压缩 frpc 与许可，不含 frps。
4. 核对 manifest 引用的归档与增量包齐全，大小与签名与产物一致。
5. 核对 Release 的资产名称、大小与 GitHub SHA-256 digest，以及 Latest 标记。

构建或上传失败时 Release 保持草稿，不会被客户端看到；但发布步骤成功后再发现资产或说明有误，需要对已发布 Release 手工处理。此流程不自动回滚应用，也不替代安装包实际升级验证；未签名产物在他人 Mac 上的首次打开、更新替换后的再次启动仍需真机验证。
