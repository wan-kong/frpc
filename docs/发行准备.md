# 发行准备

`.github/workflows/release.yml` 在推送 `v*` 标签时运行：先校验标签与 `mygo.json.version`，再在 macOS runner 上构建 `darwin/arm64` 与 `darwin/amd64`，把应用包与更新资产上传到同标签的草稿 Release。正式发布由项目所有者检查草稿后手工完成。仓库不提供发行配置脚本或资产验签脚本；日常 Go 检查只做 CLI 验证，不执行应用 build。

发行构建不做 Apple 代码签名与公证：项目没有付费开发者团队，产物只有 ad-hoc 签名。这是明确的取舍，代价见下文“Gatekeeper”。

## 已确定的身份

- 发布仓库：`wan-kong/frpc`。
- Bundle ID：`top.wankong.frpc`。
- slug 与安装包名称前缀：`frpc`。
- 支持目标：`darwin/arm64`、`darwin/amd64`；固定 MyGo 0.7.4，由 go.mod tool 提供 CLI。

代码、标签和版本元数据需先由项目所有者提交并推送。

## 版本与标签

版本只在 `mygo.json` 的 `version` 中维护。`make release` 执行 `bunx bumpp@12.3.0`（配置见 `bump.config.ts`）：提示选择 major/minor/patch，更新该字段，提交 `chore: release v<version>`，创建并推送 `v<version>` 标签。工作区不干净时直接拒绝。需要 bun，或改用 `npx bumpp@12.3.0`（Node 22.18+）。

不要在 bumpp 之后手动修改版本：workflow 会校验标签与 `mygo.json.version` 一致，不一致则不创建草稿。

## 仓库配置

只有一个 Repository Secret：

| 名称 | 用途 |
| --- | --- |
| `MYGO_UPDATER_PRIVATE_KEY` | 与 `mygo.json` 公钥配对的更新签名私钥 |

不需要 Repository Variables、证书或 Apple 公证账号。

## 更新签名

`mygo keygen` 已生成密钥，公钥写在 `mygo.json`：

```json
"updates": {
  "github": "wan-kong/frpc",
  "publicKey": "<mygo-update.pub 内容>"
}
```

私钥只通过 `MYGO_UPDATER_PRIVATE_KEY` 提供给打包环境，不得提交或随应用分发。丢失或更换私钥后，已安装版本无法再接受新更新。

## Gatekeeper

未签名（ad-hoc）应用从 GitHub 下载后带 quarantine 属性，Gatekeeper 会阻止直接打开。用户需在 Finder 中按住 Control 点击应用并选择“打开”。首次打开的手动步骤是未签名分发的既定限制；不以关闭 Gatekeeper 或全局 `xattr -cr` 作为安装指导。将来具备 Developer ID 时再在 `mygo.json` 配置 `macos.signingIdentity` 与 `notarize` 并恢复 CI 签名步骤。

## 人工核对

1. 两个架构分别产出应用包、更新归档、增量包和 `update-darwin-<arch>.json`。
2. 用 `codesign -dv`（应显示 ad-hoc）、`lipo`、`hdiutil` 核对签名类型、架构、Bundle ID 与版本。
3. 确认包内只有目标架构的压缩 frpc 与许可，不含 frps。
4. 核对 manifest 引用的归档与增量包齐全，大小与签名与产物一致。
5. workflow 上传到同标签的草稿 Release；核对资产名称、大小与 GitHub SHA-256 digest。
6. 检查草稿后再单独决定正式发布。

失败的发行流程可能留下未完整上传的草稿，不能当作已准备完成。此流程不删除已发布版本、不自动回滚应用，也不替代安装包实际升级验证；未签名产物在他人 Mac 上的首次打开、更新替换后的再次启动仍需真机验证。
